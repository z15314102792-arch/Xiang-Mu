# 项目经历｜AI 口播工作流质量治理

> 用于简历项目介绍与面试准备；区分历史项目事实、当前公开演示、尚未完成的自动剪辑能力。

## 30 秒介绍

在口播 AI 辅助剪辑实验中，遇到了自动字幕断句不符合语义、花字为凑数量乱加、音效机械跟随花字，以及口误/废片无法可靠识别的问题。我的主要工作是把这些主观反馈拆解为可描述、可记录、可复测的规则和验收项，维护问题清单，逐轮对照成片复核。后来将质量门槛、固定回归用例和规则锁定结合起来，减少修复一个问题又引发另一个问题的情况。由于不同素材特别是双说话人处理仍不稳定，原项目未完成全自动交付；这份公开演示重点呈现已形成的治理与测试方法。

## 发生过程

| 阶段 | 做过什么 | 沉淀 |
|---|---|---|
| 1. 确定问题 | 人工口播剪辑重复劳动高、效果不一致 | 把剪辑质量变成需要验收的目标 |
| 2. 分析参考 | 参考库 84 条口播成片，抽查字幕、花字、声音、节奏 | 样本观察与目标风格 |
| 3. 拆解工作流 | 粗剪、字幕、花字、音效、封面/包装 | 业务节点和质量标准 |
| 4. 记录失败案例 | 将反馈拆为单一问题、明确影响和修复要求 | 高频坏案例和问题分类 |
| 5. 固定规则 | 防止花字凑数、固定时长错位、SFX 绑花字、ASR-only 留废片 | 独立业务规则 |
| 6. 规则治理 | 单项规则锁定、变更记录、回滚设计以及历史回归 | 31 条历史规则、15→17 项历史回归记录 |
| 7. 实际验收 | 机械检查和真人看成片分开 | 技术通过 ≠ 用户认可 |
| 8. 收敛作品集 | 从原私有工程抽取无私有内容的场景 | 8 条演示规则、9 个模拟案例、网页质检器 |

**数据口径说明**：历史 31 条规则、15/17 项回归是原工程的阶段记录；本仓库只包含独立演示的 8 条规则、9 个模拟案例，不把历史数据当成本仓库实测结果。

## 如何讲一个具体问题

**花字乱加**：某一版为了达到预设密度，把普通叙述当作重点。反馈并不只是“感觉不好看”，而是“规则把数量当成了目标”。于是把花字候选限制为核心观点和有观看价值的总结，普通叙述必须舍弃，并保留这个坏案例用于复测。

**花字时机**：某一版把花字统一设成约 1.2 秒，实际讲话时长不同，导致提前消失。因此改为按真实词级起止决定出现和结束，禁止固定时长模板。

**音效机械化**：早期音效直接按花字索引派生，内容没到重点就响了。将 SFX 决策与花字拆开，以语义、重音、动作等触发条件判断。

**废片残留**：ASR 能识别说出的话，却不能可靠识别出错动作、失败重说或咳嗽。因此粗剪验收增加音频与画面双重核查，不再用“转写没有错误”替代成片复核。

## 角色边界

- **我负责**：目标判断、真实样本反馈、业务规则定义、优先级取舍、验收要求、结果评估。
- **AI 协助**：代码编写、算法调试、文件解析、部分自动化检查、测试脚本实现。
- **没有完成**：把所有人声和镜头自动分离并稳定导出商业成片；最近的新素材中 IP 和操盘手区分仍失败。
- **不能主张**：真实客户部署、节省了多少人工小时、通用剪辑系统上线、自动质检代替人审，除非未来有额外证据。

## 面试时建议现场做的演示

先选一个失败案例让系统指出问题及关联规则，再选正常案例说明“机械通过只是进入人工审核”，最后修改一处 JSON 重新运行。重点解释**为什么要这样设计规则**，而不是假装所有代码都由自己独立手写。

## 公开版与原项目的关系

当前仓库是 **脱敏、重建的教学/作品集演示**，不是直接拷贝整个私有工程。公开版的规则 ID、治理思想与错误类型来自原项目，但输入数据为合成案例，检查算法是为可移植演示重新实现的简化版本。实际媒体处理及历史回归需要在私有环境独立验证。
